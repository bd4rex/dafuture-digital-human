## 原始问题与复现（现已修复）

### 1. P2：前台请求悬挂时没有有限等待与自然兜底

- 编号：`REVIEW-AVATAR-001`。
- 位置：`public/avatar.js:975–987`、`1018–1032`。
- 触发：前台到应用服务的响应头迟迟不到，或响应头已到但 JSON 正文一直不结束；这与上游模型自己的超时是不同一跳。
- 证据：执行实际前台源码，模拟这两种网络状态，将同时支持普通定时器和 `AbortSignal.timeout` 的假时钟推进 180 秒，二者均未播报兜底。该时长已超过配置允许的 120 秒模型超时、最多 5 秒改写和额外余量。当前代码仅有人工取消用的 AbortController，没有请求截止时间。
- 影响：页面一直思考、发送按钮持续禁用，没有自然错误反馈。
- 建议：为前台请求和正文读取加统一截止时间，区分主动取消与超时；超时使用缓存话术、恢复输入，并记录本轮失败。不要恢复旧请求的晚到结果。

### 2. P2：正常业务回答中的“资料不足”被误判为拒答

- 编号：`REVIEW-MODEL-001`。
- 位置：`server.js:915–921`。
- 触发：模型使用项目明确支持的纯文本格式，回答“资料不足时，请联系工作人员补充材料，补齐后即可报名。”。
- 证据：通过真实应用路由与隔离知识库验证，同一句话放在结构化 `status: answered` 中正常返回；改为纯文本后被替换成知识不足兜底，`answerStatus` 变为 `no_answer`。
- 原因：全文拒答正则匹配“资料/信息不足”，未区分“模型不知道”和“讲解办理材料不足的情况”。
- 建议：缩小启发式拒答判断范围，保留合法业务文本；继续优先使用结构化状态，补正反例而非新增宽泛关键词。

### 3. P2：带类型的模型内容分段可能把思考文字拼进答案

- 编号：`REVIEW-MODEL-002`。
- 位置：`server.js:815–824`。
- 触发条件：兼容供应商将 `content` 返回为数组，含 `{type: "reasoning", text: "…"}` 和 `{type: "text", text: "门票免费。"}`。
- 证据：模拟该响应，服务把两个分段的 `text` 拼接，思考文字进入 `speechText`。单独的 `message.reasoning_content` 已有通过用例，不存在同一泄漏。
- 建议：明确允许的可播报分段类型，未知/思考分段不当作答案；不能靠思考文字是否恰好包含 XML 标签判断。
- 范围：这是条件性兼容契约问题，只用模拟响应复现，未声称真实已接供应商会返回这种结构。

### 4. P2：工具调用的过程文字被当作最终回答

- 编号：`REVIEW-MODEL-003`。
- 位置：`server.js:979–990`。
- 触发条件：供应商返回 `finish_reason: "tool_calls"`、`tool_calls` 字段，且 `content` 为“我需要先查询活动信息。”。
- 证据：模拟响应得到 `answered: true`，过程文字直接作为播报答案。项目没有执行工具调用循环，因此不会接着查询或提供最终答案。
- 建议：拒绝未支持的非最终完成状态，进入安全自然兜底并记录原因；本轮不要求新增工具执行功能。
- 范围：仅验证模拟响应的处理，未验证真实供应商是否产生该形态。没有正文的纯工具调用已经正确报空响应。

### 5. P2：HTTP 正文中途断流被误记为模型格式错误

- 编号：`REVIEW-HTTP-001`。
- 位置：`server.js:968–976`。
- 证据：使用原生 fetch 和两个真实本机 HTTP 服务。上游发送 HTTP 200 与未完成 JSON，然后主动断开连接，实际日志为 `MODEL_INVALID_RESPONSE` / `failureStage: response`；响应头前断开则正确归类为 `MODEL_CONNECTION_FAILED`。
- 影响：访客仍收到自然兜底，但运维会将传输故障误认为模型输出错误，不满足区分常见网络/模型故障的目标。
- 建议：将响应体读取时的传输错误与完整送达但 JSON 无效区分；保留现有超时、401/429/5xx 分类，不记录原始敏感上游正文。
